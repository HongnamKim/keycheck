# geekhack 동시 요약 설계

작성 2026-11-09. 사용자가 질문 없이 맡겼다("잘 동안 동시 요약 건도 해결해 놔"). 그래서 이 문서의 결정은 모두 Claude 판단이며, 사용자가 확인할 대상이다. 출발점은 메모리 "동시 요약 개선 예정"이다(동시 2~3건, 처리 중 플래그, 열람자 요약 진행 표시, 하루 한도 맞추기). 쓴 뒤 만드는 사람 관점과 동시성 결함 관점에서 한 번씩 점검받고 그 결과를 반영했다.

## 1. 왜 하는가

- 지금 geekhack 글 요약은 작업 하나가 5초마다 한 건씩 한다. 그래서 여러 사람이 각자 다른 미요약 글을 열면 순서대로 기다린다.
- 상세 화면의 진행 막대는 실제 상태를 모른다.
  - 차례를 기다리는 중이어도 "요약하는 중이에요"가 뜬다.
  - 막대는 화면을 연 뒤 흐른 시간만 보고 15초쯤 90%에서 멈춘다.
  - 60초가 지나면 "늦어지고 있어요"를 띄우고 확인을 멈춘다.
  - 그런데 Claude 호출은 요청 한 번의 제한 시간이 2분이고, SDK가 시간 초과·429·5xx를 기본 2번 다시 시도한다. 그래서 한 번 부르는 데 최대 6분 넘게 걸릴 수 있다.

성공한 모습: 동시 방문자가 각자 다른 글을 열어도 여러 건이 함께 요약되어 기다림이 짧다. 보는 사람은 지금 차례를 기다리는 중인지 요약 중인지 알 수 있다.

## 2. 목표와 비목표

**목표**
- geekhack 글 요약을 동시에 여러 건(설정값, 기본 2) 처리한다.
- 요약 중인 글에 처리 중 표시를 둬서 두 작업이 같은 글을 집지 않게 한다. 같은 글로 Claude를 두 번 부르거나 한도를 두 번 쓰지 않는다.
- 상세 화면에서 "차례를 기다리는 중"과 "요약하는 중"을 나눠 보여 준다. 요약 중이면 서버가 요약을 시작한 시각을 기준으로 막대를 채운다.
- 하루 요약 한도가 동시 처리에서도 맞게 센다.

**비목표** (모두 Claude 판단)
- 국내 판매 공지 요약(`NoticeSummaryWorker`)의 동시 처리. 공지는 하루 몇 건이라 지금처럼 하나씩 처리한다.
- 대기열 위치("앞에 n건")와 예상 남은 시간 표시. 확인할 때마다 순서 쿼리로 다시 세야 해서 비용에 비해 얻는 게 적다.
- 요약 순서(우선순위) 바꾸기. 조사에서 문제를 하나 찾았다: 미리 읽기로 채운 글은 사람이 열어도 최근 수집 글 뒤에 선다(`detailFetchedAt`이 예전 값 그대로라서). 하지만 운영에서 미리 읽기(`keycheck.prefetch.enabled`)가 꺼져 있어 지금은 일어나지 않는다.
- 429만 따로 다루기. SDK가 이미 물러났다가 두 번 다시 시도하고, 그래도 실패하면 지금처럼 모든 칸이 1분 쉰다.
- SDK 재시도 횟수(`maxRetries`)나 제한 시간 바꾸기.
- 백엔드 여러 대. 하루 한도처럼 서버 한 대를 가정한다.
- 공지 요약 몫을 따로 떼어 두는 한도 나누기.
- 실제 진행률. 요약은 응답 한 번으로 받아서(스트리밍 아님) 중간 진행을 알 수 없다.

**하면 안 되는 것**
- 같은 글을 동시에 두 번 요약하는 것. 그러면 Claude를 두 번 부르고 한도도 두 번 쓴다.
- 하루 한도를 넘는 것.
- 서버를 다시 띄운 뒤 처리 중 표시가 남아 글이 영영 요약되지 않는 것.
- 예외 하나로 칸이 닫히지 않은 채 남아 요약이 멈추는 것. 지금은 `@Scheduled`가 예외를 로그로 남기고 5초 뒤 다시 돌아 저절로 회복된다.
- 요약 때문에 다른 정기 작업(수집, 축소본, 공지 보관·요약)이 스레드를 기다리는 것.
- 종료가 진행 중인 요약을 기다리느라 막히는 것.
- 서버가 실제로 요약 중인데 화면이 "늦어지고 있어요"로 바뀌고 확인을 멈추는 것.
- 백엔드와 프론트 중 먼저 배포된 쪽이 다른 쪽의 옛 버전과 만나 깨지는 것.
- 자동 테스트가 실제 Claude나 geekhack을 부르는 것.

## 3. 정한 것 (모두 Claude 판단)

### 3.1 처리 중 표시는 메모리에 둔다

- 요약 중인 글의 id와 요약 시작 시각을 서버 메모리에 둔다. 여러 스레드가 함께 써도 안전한 맵을 쓰고, DB 칸은 새로 만들지 않는다.
- 이유
  - 하루 한도도 메모리에서 세는 서버 한 대 구조다.
  - 재시작하면 표시가 저절로 사라진다. 그래서 배포 중에 끊긴 글이 표시에 묶여 영영 요약되지 않는 일이 없다. 끊긴 글은 요약 대기(PENDING) 그대로라 다시 집힌다.
  - DB에 두면 오래된 표시를 풀어 주는 만료 규칙과 마이그레이션이 필요하다.
- 서버를 여러 대로 늘리면 DB 칸과 행 잠금(`FOR UPDATE SKIP LOCKED`)으로 바꿔야 한다. 그때 한도도 함께 옮긴다.

### 3.2 글 집기와 끝내기

**집기** (한 잠금 안에서 차례대로)
1. 쉬는 중(`pausedUntil`)이면 그만둔다.
2. 대상 쿼리를 부른다. `Limit`은 "이 실행에서 이미 요약한 글 수(`redone`) + 처리 중인 글 수 + 1"이다.
3. 처리 중인 글과 지금처럼 `redone`에 든 글(GB 다시 요약 대상은 빼고)을 건너뛰고 첫 글을 고른다.
4. 고른 글을 처리 중 표시에 올린다.

**한도 세기**
- 잠금 밖에서, 글을 집은 뒤에 센다.
- 한도가 차 있으면 다음 날 0시까지 쉬게 하고 그 글을 끝낸다(아래 끝내기). 먼저 세고 집기에서 지면 되돌리는 방식보다 단순하다.

**끝내기** (집기와 같은 잠금 안에서)
- 요약 성공, 글 탓 실패, API 오류, 저장 오류, 한도 초과 등 어떤 경우든 `finally`에서 한다.
- 순서
  1. 필요하면 `redone`에 넣는다(지금과 같은 경우에만).
  2. 필요하면 쉬는 시각을 정한다.
  3. 처리 중 표시를 내린다.
- 저장(DB 커밋)은 끝내기 전에 이미 끝나 있다.
- 이렇게 하는 이유는 다른 작업이 옛 조회 결과로 방금 끝난 글을 다시 집는 것을 막으려는 것이다.
  - 다른 작업이 커밋 전에 쿼리를 돌렸다면, 그 작업이 잠금을 쥔 동안 이 글의 표시는 아직 올라가 있다. 그래서 건너뛴다.
  - 커밋 뒤에 쿼리를 돌렸다면 새 상태를 본다. DONE·FAILED는 대상이 아니고, GB 다시 요약은 조건이 풀렸고, API 오류는 쉬는 시각을 이미 본다.
- 잠금 안에서 하는 일은 메모리 조작과 대상 쿼리 하나뿐이다. Claude 호출은 잠금 밖이다.

**상태 바꾸기**
- `redone`은 여러 스레드가 동시에 읽고 써도 되는 집합으로 바꾼다.
- 쉬는 시각은 더 늦은 시각만 남게 한다. 한도 때문에 다음 날까지 쉬는 것을 API 오류의 1분 쉬기가 덮어쓰지 않게 하려는 것이다.

### 3.3 동시에 돌리는 방법

**스레드 풀**
- 요약 전용 스레드 풀(Spring `ThreadPoolTaskExecutor`)을 둔다. 크기는 동시 처리 수와 같고, 줄 세우기 없이 칸 수 안에서만 넣는다.
  - 정기 작업 스케줄러의 스레드는 쓰지 않는다. 그 풀은 7개이고 `@Scheduled` 작업 수와 같아서 남는 스레드가 없다.
- 종료할 때 진행 중인 요약을 기다리지 않는다. `waitForTasksToCompleteOnShutdown=false`(기본값)에 `acceptTasksAfterContextClose=true`를 더해, 종료 단계에서 기다리지 않고 소멸할 때 곧바로 `shutdownNow`로 스레드를 깨운다. Spring 7은 앞의 값만 두면 종료 단계 제한 시간(기본 30초)까지 기다린다.
  - 종료가 시작되면(`ContextClosedEvent`) 칸은 새 칸을 열지 않고 다음 글을 집지 않는다. 버려질 Claude 호출을 새로 시작하지 않게 하려는 것이다.
  - 끊긴 글은 PENDING이라 다음 기동 뒤 다시 집힌다.
  - 그 호출은 한도에 이미 세었지만, 한도는 재시작하면 0부터 세므로 상관없다.
  - `@Bean ExecutorService`로 만들면 Java 21의 `close()`가 작업 끝을 기다리므로 쓰지 않는다.

**칸 열기**
- 스케줄러는 지금처럼 interval(5초)마다 돈다. 빈 칸이 있으면 칸 하나를 연다.
- 칸이 글을 집으면, 빈 칸이 남았을 때 칸 하나를 곧바로 더 연다. 밀린 글이 있으면 다음 틱을 기다리지 않고 동시 처리 수까지 차오르게 하려는 것이다. 대상이 없으면 새 칸은 빈 조회 한 번 하고 닫힌다.
- 열린 칸은 대상이 없어지거나 쉬는 상태가 될 때까지 다음 글을 이어서 요약한다. 지금처럼 한 건마다 5초씩 쉬지 않는다.
- 밀린 글이 없으면 지금처럼 5초마다 조회 한 번이다.

**칸 수 세기** (칸이 새서 요약이 멈추지 않게)
- 칸 수는 제출하는 쪽에서 제출 직전에 올린다. 제출이 거절되면(`RejectedExecutionException`) 바로 되돌린다.
- 칸 본문은 `try { 이어서 요약 } catch (RuntimeException e) { 로그 남기고 칸 닫기 } finally { 칸 수 내리기 }`로 감싼다.
- 예외가 묻히지 않게 `submit` 대신 `execute`를 쓴다.
- DB 예외 같은 일시 장애가 나면 칸만 닫힌다. 다음 틱에 다시 열려서 지금처럼 저절로 회복된다.

**설정**
- 동시 처리 수는 `keycheck.summary.concurrency`(기본 2)로 정한다.
  - 운영 Anthropic 조직의 요청 한도 등급은 코드로 확인할 수 없다. 칸이 쉬지 않고 이어서 돌면 지금보다 요청이 몇 배 늘 수 있다.
  - 429가 나면 모든 칸이 1분 쉬어 오히려 느려진다. 그래서 2에서 시작한다. 로그(3.7)와 429 여부를 보고 3으로 올린다.
  - 1로 두면 지금과 거의 같다. 다른 점은 칸 하나가 쉬지 않고 이어서 처리한다는 것뿐이다.
- 국내 공지 요약은 그대로 둔다. 한도는 함께 쓴다.

### 3.4 하루 한도

- 한도 카운터(`DailySummaryBudget`)는 이미 동기화되어 있다. 그래서 동시에 불러도 상한을 넘지 않는다.
- 같은 글을 두 번 세던 위험은 3.2의 처리 중 표시와 끝내기 순서로 없어진다.
- 그래서 바뀌는 것은 세 가지뿐이다: 집은 뒤에 센다는 순서, 한도가 차면 그 글을 끝내는 것, 쉬는 시각을 더 늦은 쪽으로 합치는 것.
- 하지 않는 것
  - 자정 무렵 오차. 자정 직전에 시작한 호출이 다음 날 오류로 끝나 한도를 되돌리면, 다음 날 카운터가 1 줄어든다(건당 1).
  - 공지 몫 예약. 동시 처리로 하루 2000건에 닿는 날은 일괄 다시 요약 같은 특별한 경우뿐이다.

### 3.5 상세 응답에 요약 진행 상태 더하기

- 글 상세 응답(`GET /api/posts/{id}`)에 `summarizingForMs`를 더한다. 값은 숫자 또는 null이다.
  - 지금 요약 중이면 서버가 요약을 시작한 뒤 흐른 밀리초를 넣는다.
  - 요약 중이 아니면 null이다.
  - 시각 대신 흐른 시간을 주는 이유는 브라우저와 서버의 시계 차이를 피하려는 것이다.
- 처리 중 표시는 글을 DB에서 읽기 **전에** 읽는다.
  - 순서가 반대이면 요약이 끝나는 순간 "PENDING인데 요약 중 아님"이 한 번 나올 수 있다.
  - 표시를 먼저 읽으면 남는 어긋남은 "DONE인데 요약 중"뿐이다. 이건 화면이 DONE만 보므로 해가 없다.
- 요약 상태(PENDING/DONE/FAILED)에는 새 값을 넣지 않는다. 이유는 세 가지다.
  - 국내 공지와 같이 쓰는 값이다.
  - 화면, 사이트맵, 피드가 여러 곳에서 DONE과 PENDING을 본다.
  - 프론트 타입이 닫혀 있어서, 모르는 값이 오면 요약 확인을 멈춘다.
- 확인 전용 API는 새로 만들지 않는다. 지금처럼 상세를 `fill=false`로 3초마다 다시 받는다.

### 3.6 상세 화면 표시 (`SummaryWatcher`)

**상태별 표시**

| 상태 | 문구 | 막대 |
|---|---|---|
| 첫 응답 전 | "요약 차례를 기다리고 있어요" | 기다림 표시 |
| PENDING, `summarizingForMs`가 null | "요약 차례를 기다리고 있어요" | 기다림 표시: 차오르지 않는 진행률 없는 표시. 모양은 만드는 사람이 정한다. 기존 막대 자리와 스타일 안에서 만들고, 움직임 줄이기 설정이면 지금처럼 문구만 보인다. |
| PENDING, `summarizingForMs`가 숫자 | "요약하는 중이에요" | 서버 기준 흐른 시간 t로 0.9×(1−e^(−t/τ)), τ = 10초. t는 받은 값에 받은 뒤 흐른 시간을 더한 것이다. |
| 응답에 필드가 없음(옛 백엔드) | 지금 그대로 | 지금 그대로: 화면을 연 뒤 흐른 시간 기준, τ 5초, 60초 뒤 늦어짐. 이 경로의 상수는 바꾸지 않는다(상수를 둘로 나눈다). |
| DONE, FAILED | 지금 그대로 | 지금 그대로 |

**확인 주기**
- 첫 확인은 화면이 뜨자마자 한다. 지금은 3초 뒤인데, 그동안 막대가 차올랐다가 기다림으로 돌아가는 흔들림이 생긴다.
- 그다음부터는 3초마다 확인한다.
- 확인 요청이 실패하면 직전 표시를 그대로 둔다.

**늦어짐**
- 기다림 상태가 화면을 연 뒤 180초를 넘으면 "늦어지고 있어요"를 띄우고 확인을 멈춘다. 문구는 지금과 같다.
- 요약 중인 동안에는 늦어짐으로 넘어가지 않는다. 다만 서버 기준 요약 시간이 7분을 넘으면 늦어짐으로 넘어간다. Claude 호출 한 번이 다시 시도를 포함해 최대 약 6분 넘게 걸리는 것보다 넉넉하게 잡았다.
- 요약 중이다가 다시 기다림으로 돌아가면(API 오류로 쉬는 경우) 기다림 표시로 돌아간다.

**그 밖**
- 숨겨졌다가 다시 보일 때 실행되는 정리(`useLayoutEffect` cleanup)는 받은 상태와 받은 시각도 함께 처음으로 되돌린다.
- 프론트 타입의 `summarizingForMs`는 선택 필드(`?: number | null`)로 둔다. 그래야 옛 백엔드 응답과 기존 테스트 데이터가 깨지지 않는다.

### 3.7 걸린 시간 로그

- 요약기를 부르기 전후 시간을 재서 로그에 남긴다. τ와 동시 처리 수를 실측값으로 다시 정하려는 것이다.

### 3.8 설정

- `application.yml`에 `keycheck.summary.concurrency: 2`를 더한다.
- 운영 env 예시(`deploy/keycheck.env.example`)에 주석 줄 `KEYCHECK_SUMMARY_CONCURRENCY=2`를 더한다. 하루 한도 줄과 같은 방식이다.
- interval은 5s 그대로 둔다.

### 3.9 알고 두는 것

- 다시 요약 플래그(`redo-*`)를 켜면 요약한 뒤에도 대상으로 남는 글이 `redone`에 쌓인다. 대상 쿼리의 `Limit`도 그만큼 커져서 본문까지 다시 읽는다.
- 칸이 쉬지 않고 돌면 이 조회가 지금보다 자주 일어난다.
- 운영에서는 플래그가 꺼져 있어 영향이 거의 없으므로 지금은 기록만 한다.

## 4. 테스트

- **작업자**
  - 두 스레드가 동시에 `summarizeNext`를 부르면 서로 다른 글을 집는다. 요약기 안에서 latch로 붙잡아 확인한다.
  - 한도는 글마다 한 번만 센다.
  - 요약 성공, 글 탓 실패, API 오류, 저장 예외, 한도 초과 뒤 처리 중 표시가 내려간다.
  - 한도가 차면 쉰다.
  - 쉬는 시각은 더 늦은 값이 남는다.
- **칸 여닫기**
  - 틱마다 빈 칸이 있으면 하나를 연다.
  - 글을 집은 칸은 빈 칸이 있으면 하나를 더 연다.
  - 동시 처리 수를 넘지 않는다.
  - 열린 칸은 대상이 있는 동안 이어서 처리하고, 없으면 닫힌다.
  - 칸 안에서 예외가 나도 칸 수가 돌아오고 로그가 남는다.
  - 제출이 거절되면 칸 수를 되돌린다.
- **상세 응답**: 요약 중인 글은 `summarizingForMs`가 시작한 뒤 흐른 시간이고, 아닌 글은 null이다.
- **프론트(lib)**
  - 첫 응답 전, 기다림, 요약 중, 옛 백엔드 네 경우의 문구와 막대 값을 확인한다.
  - 기다림 180초 늦어짐, 요약 중에는 늦어지지 않음, 요약 7분 상한을 확인한다.
  - 옛 백엔드 경로의 기존 기대값(τ 5초, 60초)은 그대로 통과해야 한다.
- 기존 `SummaryWorkerTest`의 순서·다시 요약 테스트는 그대로 통과해야 한다.

## 5. 배포

- 마이그레이션은 없다.
- 백엔드와 프론트 어느 쪽을 먼저 배포해도 된다. 새 프론트는 필드가 없으면 예전처럼 보이고, 옛 프론트는 새 필드를 무시한다.

## 6. 만드는 사람에게 맡기는 것

- 클래스 이름과 위치. 처리 중 표시를 보관하는 쪽과 칸을 여는 쪽을 기존 패키지 규칙(도메인 아래 역할별 폴더) 안에서 정한다.
  - 상세 응답을 만드는 `post` 쪽이 처리 중 표시를 읽어야 한다. 표시 보관소가 다른 빈에 기대지 않게 만들어 빈 순환을 피한다.
- 기다리는 동안 보일 표시의 모양.
- 동시성 테스트를 짜는 방식(latch, executor).
- 설정값을 담을 곳. 기존 `SummaryProperties`에 더하면 테스트의 생성자 호출(약 20곳)을 함께 고친다.
