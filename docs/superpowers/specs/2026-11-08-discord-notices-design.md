# 국내 판매 소식(디스코드 공지) 설계

작성 2026-11-08. 인계 노트: 옵시디언 `Keycheck/디스코드 공지 수집 작업 계획.md`.

## 1. 왜 하는가

- 국내 판매처(Swagkeys, GeonWorks)는 판매 소식을 디스코드 공지 채널에 올린다. 공지는 대화방처럼 글이 위로 밀려 쌓이기만 해서 **훑어보는 것 자체가 불편하다**. geekhack에서 겪은 문제와 같다(사용자).
- geekhack 글을 한국어 요약·대표 이미지·원문 링크로 정리했듯, 디스코드 공지 중 **판매 소식만** 골라 판매 건 하나를 카드 하나로 정리해 키체크에서 보여 준다.
- 판매 시각을 놓치지 않게 돕는 표시도 넣는다. 다만 알림은 없다. 로그인·관심 상품 표시가 없으므로 목록 카드의 배지로만 알린다(사용자 결정).

성공한 모습: 디스코드를 열어 스크롤하지 않아도 키체크에서 최근 국내 판매 소식을 geekhack 소식처럼 한눈에 훑고, 곧 시작하거나 곧 끝나는 판매가 바로 눈에 들어온다.

## 2. 목표와 비목표

**목표**
- 백엔드가 봇 토큰으로 두 판매처 공지 채널을 주기적으로 읽어 원문을 저장하고, 첨부 이미지를 받는 즉시 R2에 보관한다.
- Claude가 공지 하나를 판매 건 단위로 나누고 한국어로 요약한다. 판매가 아닌 공지는 0건이다.
- 화면: 헤더 메뉴 "국내 판매"와 목록 페이지, 판매 건 상세 페이지, 메인의 국내 판매 가로 줄, 메인 하이라이트 아래 국내 판매 띠, 하이라이트 큰 칸에 국내 판매를 무작위로 노출한다.
- 2026-06-01 이후의 지난 공지를 봇 수집과 같은 경로로 미리 채운다(운영 DB 포함).

**비목표**
- 알림(푸시·메일), 로그인, 관심 상품 표시(사용자 결정).
- 같은 상품의 여러 공지(예정 → 시작 → 마감)를 하나로 묶기, geekhack 글과 같은 상품끼리 잇기. 나중에 한다.
- 공지 수정·삭제 따라가기. 처음 받은 내용으로 처리한다(Claude 판단).
- 디스코드 임베드 미리보기 이미지(스마트스토어·유튜브 썸네일), 반응 수. 반응 수는 팔로우 채널 사본에 따로 쌓여 원래 서버 값을 알 수 없다.
- RSS에 넣기, 판매 건별 공유 미리보기 이미지(사이트 기본 이미지를 쓴다). Claude 판단.
- Swagkeys·GeonWorks 말고 다른 판매처.

**하면 안 되는 것**
- 공지에 없는 주소로 링크하는 것(AI가 지어낸 주소). 구매 링크는 그 공지 본문에 있던 링크 중 하나여야 한다.
- 판매가 아닌 공지(배송 지연·발송 안내, 가격 인상, 타건샵·팝업·행사, 아르바이트, A/S, 유튜브·라이브 방송 소식)나 키보드 밖 제품(마우스, 장패드, 케이블, 굿즈·액세서리)을 화면에 보여 주는 것(사용자 결정).
- 모든 카드가 중요해 보이게 강조하는 것. 강조색은 정말 임박한 판매에만 쓴다(사용자).
- 사용자 디스코드 계정을 프로그램으로 조작하는 것(셀프봇·내보내기 프로그램 — 약관 위반·계정 정지 위험). 지난 공지는 사용자가 손으로 불러오고 복사한다.
- 공지 원문·이미지를 저장소에 커밋하는 것. 비밀값(봇 토큰)을 셸 명령·채팅에 싣는 것.
- 자동 테스트가 실제 디스코드·Anthropic·R2를 부르는 것.
- 비용이 드는 요약 실행(지난 공지 채우기)을 건수·예상 비용 확인 없이 돌리는 것.
- 화면 문구에 "해외". 문구는 해요체.

## 3. 정한 것

### 3.1 무엇을 모으는가 (사용자 결정)

- **판매 소식**: 예약판매, 드랍, 판매 시작, 래플, 재입고(판매 시작 시각이나 구매 링크처럼 살 수 있는 정보가 있는 재입고), 그리고 이런 판매의 예고·일정 변경(연장·마감 안내).
- **제품 범위**: 키보드(완제품·키트), 키캡, 스위치, 키보드 부품(기판·보강판·스테빌라이저 등). 윤활제·공구는 키보드 밖으로 본다(Claude 판단).
- 같은 상품이라도 "판매 예정" 공지와 "판매 시작" 공지는 따로 항목이다(geekhack IC와 공동구매처럼). 공지마다 판매 건을 만들고 공지끼리 합치지 않으므로 자연히 따로 나온다.
- 대표 링크는 구매 페이지다. 디스코드 메시지 링크는 그 서버 회원만 열려서 쓰지 않는다.

### 3.2 수집 (백엔드)

- **방식**: 백엔드가 봇 토큰으로 디스코드 REST API를 주기적으로 조회한다(사용자 결정. 봇이 우리 API로 보내는 방식은 쓰지 않는다). geekhack 정기 수집과 같은 모양의 `@Scheduled` 스케줄러, 켜고 끄는 설정(`NOTICE_ENABLED`, 기본 꺼짐 — 운영에서만 켠다).
- **채널**: 사용자 디스코드 서버의 채널이 두 판매처 공지 채널을 팔로우하고 봇이 그 채널을 읽는다. 설정 `DISCORD_BOT_TOKEN`, `SWAGKEY_CHANNEL_ID`, `GEONWORKS_CHANNEL_ID`(이미 `backend/.env`에 있음 — `.env.example`, `deploy/keycheck.env.example`에도 이름을 추가한다). 채널 → 판매처 대응은 설정으로 둔다. 판매처는 기존 `KoreanVendor`의 `SWAGKEYS`, `GEONWORKS`를 쓴다.
- **조회**: 채널마다 `GET /channels/{id}/messages?after=<그 채널에서 받은 마지막 메시지 id>&limit=100`. 커서가 없으면(첫 실행) 최근 100개부터. 100개가 차면 이어서 더 받는다. 429는 `retry_after`만큼 쉰다. 주기는 5분(Claude 판단).
- **메시지 고르기**: 보통 메시지(type 0)만 받는다. 팔로우 알림(type 12) 같은 시스템 메시지는 버린다.
- **원래 메시지 id**: 팔로우 채널의 메시지는 크로스포스트 사본이라 자기 id와 별도로 `message_reference.message_id`에 원래 서버의 메시지 id가 있다(flags 2, 샘플로 확인). **원래 id를 공지의 고유 키**로 쓴다. 지난 공지(원래 서버에서 복사)와 봇 수집분이 겹쳐도 한 번만 저장된다. 사본 id는 커서용으로 따로 둔다.
- **원문 저장(사용자 결정)**: 받은 메시지 JSON을 통째로 DB에 둔다(메시지 하나가 한 줄). 첨부의 디스코드 주소(`url`, `proxy_url`) 자리는 R2에 보관한 사본을 가리키게 바꾼다(3.3). 원문은 DB에만 있고 화면에 그대로 내보내지 않는다.
- **사진만 있는 메시지(Claude 판단)**: Swagkeys는 공지 글을 올린 뒤 사진을 따로 올리기도 한다(복사본 150개 중 6개. 17초~74분 뒤). 본문이 비었거나 역할 멘션(@KR 등)만 있고 첨부가 있는 메시지는, 같은 채널에서 그보다 앞서 24시간 안에 올라온 가장 최근 글 공지에 **딸린 메시지**로 묶는다. 딸린 메시지는 따로 요약하지 않고, 그 사진은 앞 공지의 첨부 뒤에 시간 순으로 붙는다. 묶을 공지가 없으면 판매 0건으로 끝낸다.

### 3.3 첨부 이미지 보관

- 디스코드 첨부 주소는 하루쯤 뒤 만료된다(주소의 `ex=`). 그래서 **요약할 때가 아니라 공지를 받는 즉시** 내려받아 R2에 올린다(사용자 동의). 요약이 한도·실패로 늦어져도 사진을 잃지 않는다.
- 크기 세 가지, 모두 기존 `ThumbnailMaker`(WebP, 확대하지 않음)로 만든다.
  - 폭 2048: 원본 대신 보관하는 사본(원본은 장당 수 MB~12MB라 그대로 두지 않는다 — 사용자 동의). 넓은 자리(하이라이트 큰 칸·띠, 상세 위 사진)에도 이것을 보여 준다(2026-11-08 시안 확인 때 사용자 지적: 1280은 넓은 자리에서 흐리다).
  - 폭 1280: 중간 크기 자리용으로 남겨 둔다.
  - 폭 640: 카드·목록.
- 보관할 때 원본 사진의 폭·높이를 첨부에 저장한다(하이라이트 사진 조건에 쓴다, 3.8).
- 키 이름은 기존 `thumbs/…`와 겹치지 않게 공지용 접두어와 디스코드 첨부 id(전역 고유)로 짓는다(예: `notices/<첨부 id>-640.webp`). 딸린 메시지의 사진도 같은 규칙이라 어느 공지에 묶이든 키가 바뀌지 않는다. DB에는 키만 저장하고 주소는 `ThumbUrls`처럼 공개 주소 + 키로 만든다(기존 방식).
- 내려받기는 기존 `ImageDownloader`(SSRF 방어, 25MB 상한)를 쓴다. 실패하면 몇 번 다시 시도하고, 봇으로 받은 공지는 메시지를 다시 조회하면 새 첨부 주소를 받을 수 있다. 끝내 실패한 첨부는 실패로 표시하고 그 사진 없이 진행한다.
- 요약 대상: 올라온 지 10분이 지났고, 자기와 딸린 메시지의 이미지 보관이 끝난(또는 실패로 끝난) 글 공지. 10분은 바로 뒤따르는 사진을 기다리는 시간이다(Claude 판단).
- 요약이 끝난 뒤에 딸린 메시지가 들어오면(74분 뒤 사례) 그 공지를 다시 요약 대상으로 되돌린다. 다시 요약하면 판매 건을 새로 만든다(3.4).

### 3.4 판매 건 나누기·요약 (Claude)

- 기존 요약과 같은 모양: `NoticeSummarizer` 인터페이스, Claude 구현(공식 Anthropic Java SDK, 구조화 출력 JSON 스키마, 같은 모델 설정 `keycheck.claude.*`), 가짜 구현(테스트·개발 기본). 같은 `SUMMARIZER` 설정으로 바꾼다.
- **보내는 것**: 판매처, 공지 시각(한국 시각), 본문, 본문 링크 목록(`글자 | 주소`), 첨부 목록(순번·파일 이름, 딸린 메시지의 사진 포함)과 640 사본 이미지(어느 사진이 어느 상품인지 고르게). 본문의 디스코드 시간 표기 `<t:유닉스초:형식>`는 보내기 전에 한국 시각 글자로 바꾼다. "금일", "차주 화요일" 같은 말은 공지 시각을 기준으로 AI가 날짜로 바꾼다.
- **받는 것**: `items: [...]`. 판매 건마다
  - `productName`: 상품 이름(원문 표기, 80자까지).
  - `category`: `KEYBOARD`, `KEYCAP`, `SWITCH`, `PARTS`, `OTHER`. 키보드 밖 제품은 `OTHER`로 받아 저장하되 화면·API에서 뺀다(범위가 바뀌어도 다시 요약하지 않게 — Claude 판단).
  - `saleType`: `SALE`(일반 판매), `PREORDER`(예약판매), `RESTOCK`(재입고), `DROP`(드랍), `RAFFLE`(래플).
  - `phase`: `ANNOUNCE`(예고), `OPEN`(판매 시작·진행), `CHANGE`(일정 변경·연장·마감 안내).
  - 판매 시작·마감: 각각 날짜(`YYYY-MM-DD`)와 시각(`HH:mm`)을 따로 받는다. 날짜를 모르면 둘 다 null, 날짜만 알면 시각만 null(예: "11/12 판매 시작"). 저장도 "시각을 모름"을 구분해 둔다(Claude 판단 — 자정으로 저장하면 "5시간 뒤 시작" 같은 배지가 틀리고, null로 두면 날짜까지 잃는다).
  - `shippingNote`: 배송 일정 글(예: "27년 3분기 발송 예정"), 없으면 null.
  - `summary`: 한국어 해요체 1~3줄.
  - `links`: 이 판매 건의 구매 링크들(`{text, url}`). **넘긴 링크 중에서만**.
  - `images`: 이 판매 건의 첨부 순번들, 첫 번째가 대표 사진. 없으면 빈 배열.
- **검증**: 넘긴 링크에 없는 주소는 버린다(기존 벤더 링크 검증과 같은 방식). 없는 첨부 순번은 버린다. 이름이 빈 항목은 버린다. 시각을 읽을 수 없으면 null. 판매 건은 공지당 최대 20개.
- 다시 요약하면 그 공지의 판매 건을 지우고 새로 만든다.
- **하루 한도**: 기존 하루 요약 한도(2,000건, 한국 날짜 기준)를 geekhack 요약과 **같이 쓴다**. 한도의 목적이 전체 비용이라서다(Claude 판단). 지금 `SummaryWorker` 안에 있는 세기를 두 작업이 같이 쓰는 부품으로 꺼낸다.

### 3.5 저장 구조

- **공지(원문, 메시지마다 한 줄)**: 원래 메시지 id(고유), 사본 id(봇 수집분만), 채널, 판매처, 출처(`BOT`/`BACKFILL`), 작성 시각, 원문 JSON, 딸린 메시지면 앞 공지, 첨부 목록(첨부 id, 파일 이름, 크기, R2 키 세 개, 실패 횟수), 이미지 보관 상태, 요약 상태(`PENDING`/`DONE`/`FAILED`, 딸린 메시지는 요약하지 않음), 요약한 모델, 요약 시각.
- **판매 건**: 공지, 공지 안 순서, 판매처, 공지 시각(정렬용), 3.4의 항목들(시작·마감은 시각을 아는지 함께), 숨김 여부(잘못 나온 건을 손으로 숨기기 — 기존 `post.hidden`과 같은 쓰임).
- Flyway 마이그레이션으로 새 테이블을 만든다(V13부터).

### 3.6 상태 배지 (사용자 결정: 시안 A "배지만")

카드 위쪽 줄 맨 앞에 상태 배지 하나. 카드 테두리·사진은 건드리지 않는다. 지금 시각과 판매 시각으로 계산한다(한국 시각, 서버에서 목록을 받은 시각 기준 — 기존 공동구매 칩과 같은 방식).

| 상태 | 조건 | 배지 | 모양 |
|---|---|---|---|
| 곧 시작 | 시작까지 24시간 이하 | "5시간 뒤 시작"(1시간 안이면 분) | 강조색 채움 |
| 시작 예정 | 시작까지 24시간 넘음 | "D-4 시작" | 회색 테두리 |
| 곧 마감 | 판매 중이고 마감까지 48시간 이하 | "D-2 마감", 24시간 안이면 "5시간 뒤 마감" | 강조색 채움 |
| 판매 중 | 시작했고 마감 전(마감 시각이 없으면 시작 뒤 7일까지) | "판매 중" | 진한 테두리 |
| 종료 | 마감 시각이 지남 | "판매 종료" | 회색 테두리 |
| 일정 미정 | 예고인데 시작 시각이 없음 | "일정 미정" | 회색 점선 |

- 시작 날짜가 없는 `OPEN`은 공지 시각을 시작으로 본다. 마감 없이 7일이 지나면 배지를 달지 않는다(아직 파는지 알 수 없어서 — Claude 판단).
- **날짜만 알 때(Claude 판단)**: 날짜 단위로만 말한다. 시작이 오늘이면 "오늘 시작"(강조색 채움), 내일 이후면 "D-n 시작"(회색 테두리). 마감 날짜만 알면 그날 끝(23:59)까지 판매 중으로 보고, 오늘이면 "오늘 마감", 내일이면 "D-1 마감"(둘 다 강조색 채움). 시간 단위 배지("5시간 뒤 …")는 시각을 알 때만 쓴다.
- 강조 기준(24시간·48시간)은 Claude 판단이다.
- 카드의 구분 글자: `saleType` 이름(판매·예약판매·재입고·드랍·래플)에 `ANNOUNCE`면 " 예정", `CHANGE`면 " 일정 변경"을 붙인다. 예: "Swagkeys · 재입고 예정", "GeonWorks · 판매 시작"(SALE+OPEN은 "판매 시작").

### 3.7 화면

- **헤더 메뉴**: IC, 공동구매 옆에 "국내 판매"(`/sales`).
- **목록 `/sales` — 타임라인 두 가지(2026-11-08 샘플 요약 뒤 사용자 결정)**: 실제 데이터에서 사진 있는 판매 건이 21%뿐이라(GeonWorks 302건 중 2건) 사진 카드 격자 대신 타임라인으로 그리고, 두 보기를 모두 제공해 사용자가 고른다.
  - 위쪽 탭 "공지 순 | 판매 일정 순", 주소 `view=schedule`(기본은 공지 순, 주소에서 뺀다). 판매처·분류 필터는 두 보기에 같이 적용. 분류 칩 이름은 전체·키보드·키캡·스위치·기타(사용자 결정: "부품" 대신 "기타", 값은 그대로 PARTS — 기판·보강판·스테빌라이저·흡음재 등).
  - **공지 순(A)**: 날짜 머리(오늘·어제·M월 D일 요일) → 공지 묶음(판매처, "HH:mm 공지 · 판매 N건") → 판매 건 줄. 이어 받기는 지금처럼(페이지 경계에서 같은 공지는 이어 붙인다).
  - **판매 일정 순(B)**: 곧 마감(판매 중이고 7일 안에 마감) → 오늘 → 내일 → 이번 주(6일 안) → 다음 주 이후(시작 예정) → 판매 중 → 일정 미정 순 구간. 끝난 판매는 빼고, 마감 없는 판매 중은 시작(없으면 공지) 뒤 7일까지, 일정 미정은 공지 30일 안만. 구간 안은 해당 시각 이른 순.
  - **판매 건 줄**(두 보기 공통): 사진이 있으면 왼쪽 작은 썸네일(640), 상태 배지 + 구분(B에서는 판매처도), 상품 이름, 판매 시각 글. 줄 전체가 상세 링크.
  - 상세의 "목록으로"는 보던 보기로 돌아간다. 메인 가로 줄은 사진 카드 그대로(Claude 판단).
- 목록 제목 "국내 판매"와 설명 "Swagkeys·GeonWorks 디스코드 공지에서 판매 소식만 골라 정리했어요."(사용자 결정: "한국어로"는 빼기). 공지 시각 최근 순. 필터는 판매처(전체·Swagkeys·GeonWorks)와 분류(전체·키보드·키캡·스위치·부품). 끝난 판매도 "판매 종료" 배지를 달고 남긴다(Claude 판단). 카드 모양은 기존 목록 카드(`PostCard`)를 따른다: 사진(640), 배지 줄(상태 배지 + 판매처 · 구분), 상품 이름, 요약 첫 줄, 판매 시각 줄, 공지 날짜.
- **상세 `/sales/[id]`** (Claude 판단 — geekhack 글처럼 카드는 키체크 상세로 가고, 상세에서 구매 페이지로 간다): 상태 배지·판매처·구분, 상품 이름, 요약, 정보(판매처, 구분, 판매 시작, 마감, 배송 일정), 구매 링크 버튼들(새 탭), 위 큰 사진은 2048, 이 판매 건으로 분류된 사진만 모은 사진 모음(2장 이상일 때만, 확대 보기), "디스코드 공지 11/6(금) 18:52"(링크 없이 글자), 목록으로.
- **메인 가로 줄**: 공동구매 줄 아래 "03 국내 판매". 최근 판매 건 10개, "전체 보기 →"는 `/sales`. 하이라이트 아래 바로 가기 줄에도 "국내 판매"를 더한다. 하이라이트 소개 글에서 geekhack만 말하는 부분을 국내 판매까지 포함하게 고친다.
- **하이라이트 아래 국내 판매 띠(사용자 결정: 시안 C)**: 기존 여섯 칸 아래 넓은 띠 한 줄. 3.8에서 고른 국내 판매 하나를 사진·키커("곧 시작하는 국내 판매" 등)·상품 이름·상태 배지로 보여 준다. 모양은 밝은 카드(시안 v4의 띠 A: 왼쪽에 3:2 사진, 오른쪽에 키커·이름·배지·판매처·구분·판매 시각, "자세히 →") — 사용자가 A·B 모두 좋다며 맡겼고, 사진이 덜 잘리고 "별도 영역" 취지에 맞아 A로 정함(Claude 판단). 사진은 2048, 화면 아래쪽이라 늦게 불러온다.
- **하이라이트 큰 칸 (사용자 결정)**: 접속할 때마다 반반 확률로 geekhack 큰 칸 후보와 국내 판매 1순위 중 하나를 보여 준다.
  - 국내 판매 후보가 없으면 늘 geekhack.
  - 큰 칸에 국내 판매 1순위가 나오면 띠에는 2순위를, 2순위가 없으면 띠를 감춘다. geekhack이 나오면 띠에는 1순위.
  - 국내 판매일 때 큰 칸은 geekhack 반응(조회·댓글) 자리에 판매처·구분·판매 시각을, 키커는 고른 기준대로 붙인다.
  - 검색·미리보기 봇에는 늘 geekhack 쪽을 보여 준다.
  - **고르기는 브라우저에서 한다(Claude 판단)**: 메인은 SEO 캐시 작업에서 정적(재검증 1분, 만료 15분)이 됐고 "메인으로"가 5분 안이면 바로 뜬다(사용자 요청). 서버에서 요청마다 고르면(`headers()`, 무작위) 이 두 가지를 잃는다. 그래서 정적 화면에 두 가지 모양(geekhack 큰 칸 + 띠 1순위 / 국내 판매 큰 칸 + 띠 2순위)을 함께 넣고, 화면을 그리기 전에 도는 작은 인라인 스크립트가 반반으로 하나를 골라 표시를 정한다(테마 스크립트와 같은 방식이라 깜빡임이 없다). 스크립트는 `navigator.userAgent`가 봇이면(기존 `isCrawler`와 같은 규칙) 고르지 않는다. 스크립트가 돌지 않으면 geekhack 쪽이 보인다. 고른 값은 새로고침할 때마다 바뀌고, 사이트 안에서 메인으로 돌아올 때는 그대로다.
- **시안 먼저**: 목록·상세·띠·큰 칸의 국내 판매 모양은 구현 전에 시안으로 보여 주고 확인받는다(사용자 원칙). 기존 색·글꼴·배지 크기를 따른다.

### 3.8 하이라이트용 국내 판매 고르기 (사용자 결정)

대상: 숨기지 않았고 `OTHER`가 아니며 대표 사진이 있고, 그 대표 사진 원본 폭이 1024px 이상인 판매 건(넓은 자리에서 흐리지 않게 — 2026-11-08 사용자 지적, 샘플 394장 중 약 20%가 1024px 미만). 위에서부터 차례로 채워 최대 2개를 고른다.

1. **곧 시작**: 7일 안에 시작하는 것, 이른 시작 순.
2. **곧 마감**: 판매 중이고 7일 안에 끝나는 것, 이른 마감 순.
3. **최근 소식**: 14일 안에 올라온 것, 최근 순.

같은 판매 건은 한 번만. 날짜만 아는 시작·마감은 그날 안의 시각 아는 것들 뒤에 둔다(Claude 판단). 키커는 실제로 고른 단계에 맞춰 "곧 시작하는 국내 판매", "곧 마감하는 국내 판매", "최근 국내 판매 소식". 하나도 없으면 띠를 그리지 않는다.

### 3.9 API

- `GET /api/sales`: 목록(판매처·분류 필터, 기존 글 목록과 같은 방식으로 이어 받기). 카드에 필요한 값(이름, 판매처, 구분, 시작·마감, 요약 첫 줄, 대표 사진 640·1280·2048 주소, 공지 시각).
- 카드에 `noticeId`(공지 묶음용)를 더한다.
- `GET /api/sales/schedule`: 판매 일정 순 보기용(판매처·분류 필터, 이어 받기 없음, 최대 300건). 끝나지 않은 판매만: 마감이 지금 이후, 또는 마감 없이 시작(없으면 공지) 뒤 7일 안, 또는 시작 예정, 또는 일정 미정이면 공지 30일 안.
- `GET /api/sales/{id}`: 상세(요약 전부, 배송 일정, 링크들, 사진들 1280·640).
- `GET /api/sales/highlights`: 3.8의 최대 2개와 각각 고른 단계.
- `GET /api/sales/sitemap`: 사이트맵용 id 목록. 사이트맵에 `/sales`와 상세를 넣는다.
- 모두 GET, 기존 CORS 설정 범위(`/api/**`). 숨김·`OTHER`·요약 전 공지는 내보내지 않는다.

### 3.10 지난 공지 채우기 (사용자 결정)

설계·구현이 끝난 뒤 마지막에 한다(사용자 결정). 봇 수집과 **같은 경로**로 넣는다(원래 계획인 "요약값만 마이그레이션"을 바꿈). 2026-11-08에 `backfill/_inbox/`에 저장한 Swagkeys 복사본 두 개(6/1~11/6, 145개)는 **구현 중 샘플 데이터**로 쓴다(사용자 결정). 같은 날 메시지 JSON(`backfill/swagkeys/messages.json`)으로 바꾸고 첨부를 만료 전에 내려받았다. 마지막 채우기 때 이 묶음을 그대로 쓸 수 있고, 빠진 8/20과 그 뒤 새 공지, GeonWorks만 새로 복사하면 된다.

1. 사용자가 디스코드(웹)에서 판매처 공지 채널을 2026-06-01 이전까지 불러온 뒤, 개발자 도구로 페이지 HTML을 복사한다. 판매처마다, 필요하면 여러 번.
2. 세션이 **즉시** 클립보드를 `.superpowers/work/discord/backfill/<판매처>/`에 저장하고, 일회용 스크립트(저장소에 넣지 않음)로 메시지를 디스코드 API 모양 JSON(원래 메시지 id, 작성 시각, 본문, 첨부 id·파일 이름)으로 바꾸고, **첨부 이미지를 바로 내려받는다**(가장 빠른 만료가 복사 뒤 약 12시간). 본문은 화면 HTML을 디스코드 마크다운에 가깝게 되살린다(제목 `##`, 목록 `-`, 링크 `[글자](주소)`, 시간 표기는 `<time datetime>`에서 `<t:초:F>`로).
3. 받은 공지·링크·사진 수를 보고한다. 복사본 사이 빈 날(예: 확인 때 본 8/20)이 있는지 확인한다. 2026-06-01(한국 시각) 이전 공지는 버린다.
4. 요약 건수와 예상 비용을 보고하고 확인받는다.
5. **로컬 확인**: 같은 가져오기를 로컬 DB·개발 R2에 돌려 결과를 본다.
6. **운영**: 사용자가 JSON과 이미지 묶음을 서버로 옮기고, 같은 이미지로 일회성 가져오기를 실행한다(공개 API를 만들지 않는다 — 예: `docker compose run --rm`에 가져오기 폴더를 붙이고 가져오기 설정을 준다). 서버가 자기 R2에 사진을 올리고 원문을 `BACKFILL`로 저장한다. 요약은 평소 요약 작업이 처리한다.
- 이미 있는 원래 메시지 id는 건너뛴다(봇이 먼저 받은 11/5 이후 공지와 겹침).
- 가져오기는 메시지를 시간 순으로 넣고 수집과 같은 "딸린 메시지" 규칙을 쓴다. 변환 스크립트에서 메시지를 합치지 않는다.
- 가져오기 코드는 백엔드에 넣고 테스트한다(손으로 쓴 JSON). HTML을 JSON으로 바꾸는 스크립트는 디스코드 화면 구조에 묶인 일회용이라 넣지 않는다.

### 3.11 운영

- 서버 환경변수 파일(`/etc/keycheck/keycheck.env`)에 `DISCORD_BOT_TOKEN`, 채널 id 두 개, `NOTICE_ENABLED=true`를 사용자가 편집기로 직접 넣는다.
- 확인용으로 띄운 서버가 로컬 DB의 수집 상태를 바꾸지 않게 한다(수집은 기본 꺼짐).

## 4. 테스트

- 디스코드 클라이언트: 가짜 서버(`MockRestServiceServer`)로 조회·이어 받기·429.
- 수집: 크로스포스트의 원래 id 쓰기, type 12 버리기, 이미 있는 공지 건너뛰기, 채널별 커서, 사진만 있는 메시지를 앞 공지에 묶기(24시간 경계, 묶을 공지 없음), 요약 뒤 딸린 메시지가 오면 다시 요약 대상으로.
- 이미지 보관: 가짜 저장소(`FakeThumbStorage`)와 로컬 서버로 세 크기 저장, 원문 JSON 첨부 주소 바꾸기, 실패·다시 시도·끝내 실패.
- 요약기: 가짜 Anthropic 서버로 시간 표기 바꾸기, 없는 링크·없는 첨부 순번 버리기, 시각 읽기, `OTHER` 저장, 판매 아닌 공지 0건, 스키마.
- 하루 한도: 두 요약이 같은 세기를 쓴다.
- 하이라이트 고르기: 세 단계 순서, 2개까지, 사진 없는 건·`OTHER`·숨김 제외.
- API: 필터, 숨김·`OTHER`·요약 전 제외.
